# 위치 데이터를 어떻게 모으고 보관할지 — 제안

2026-09-17 · 결정 요청 문서

---

## 한 줄 요약

**위치를 "찍은 그대로 전부" 보관하는 대신, "어디에 얼마나 머물렀는지"로 정리해서 보관하자**는 제안입니다.
같은 정보를 담으면서 서버 비용이 **10분의 1 수준**으로 줄어듭니다.

---

## 1. 지금 무슨 일이 벌어지고 있나

어제 실제로 측정한 내용입니다. 휴대폰을 책상에 4시간 올려두었습니다.

- 위치를 **270번** 확인해서 **270건**을 저장했습니다
- 그런데 실제로 기록된 장소는 **4곳**뿐이었습니다 (그것도 서로 2미터 거리)

**같은 자리를 266번 다시 적은 셈입니다.**

사람은 하루의 대부분을 한자리에 있습니다. 회사에 8시간, 집에 10시간. 그동안 위치는 바뀌지 않는데, 지금 방식은 그 시간 내내 같은 좌표를 계속 저장합니다.

거동이 불편해 **집에만 계신 분**은 더합니다. 한 달이면 약 24,000건이 쌓이는데 전부 같은 좌표입니다.

## 2. 다른 회사들은 어떻게 하나

가족 위치 공유 앱(Life360 등)과 이 분야의 일반적인 방식을 조사했습니다.

| 항목 | 업계 방식 | 라무핀 현재 |
|---|---|---|
| 위치 확인 간격 | 상황에 따라 다르게 (움직이면 자주, 가만히 있으면 드물게) | **어제 같은 방식으로 바꿈** |
| 걷는지 차를 탔는지 구분 | 휴대폰 센서로 판별 | **어제 기능 추가함** |
| 여러 건을 묶어서 전송 | 함 | 하고 있음 |
| 실내에서는 Wi-Fi 활용 | 함 (사용자에게 "Wi-Fi 켜두세요" 안내) | 기능은 되나 **안내 없음** |
| **보관 방식** | **"머문 곳"으로 정리해서 보관** | **찍은 것 전부 보관** |

앞의 네 가지는 이미 맞췄거나 간단히 맞출 수 있습니다.
**마지막 하나가 남았고, 이게 비용에서 가장 큰 차이를 만듭니다.**

## 3. "머문 곳으로 정리한다"는 게 무슨 뜻인가

지금 저장되는 모습 (예시)

```
09:00:00  가산동 사무실
09:03:00  가산동 사무실
09:06:00  가산동 사무실
      ... (8시간 동안 160번 반복) ...
17:00:00  가산동 사무실
```

정리해서 저장하면

```
09:00 ~ 17:00   가산동 사무실에 머무름
```

**160건이 1건이 됩니다.** 그리고 보호자가 보는 화면에는 차이가 없습니다. 오히려 "8시간 머물렀다"가 한눈에 보여서 더 낫습니다.

이동 중에는 지금처럼 촘촘히 기록합니다. 이동 경로는 실제로 계속 바뀌니까요.

### 단, 반드시 지켜야 할 조건

**아무리 오래 같은 곳에 있어도 하루 단위로는 끊어서 기록해야 합니다.**

집에만 계신 분을 "한 달 내내 집" 1건으로 뭉쳐 버리면, **"어제 살아 계셨나"를 확인할 근거가 사라집니다.**
이 앱에서 그건 치명적입니다. 하루에 최소 1건은 남겨야 합니다.

또 하나, **"안 움직였다"는 기록도 함께 남겨야 합니다.** 집에만 계신 분은 위치로는 아무 일도 없어 보이지만,
휴대폰이 감지한 움직임(걷기·정지)이 있어야 "평소처럼 지내시는지 / 쓰러져 계신지"를 구분할 수 있습니다.
자세한 내용은 [anomaly-alerts.md §6](./anomaly-alerts.md)에 있습니다.

## 4. 얼마나 줄어드나 (10만 대 기준)

| | 6개월 보관량 | 월 서버 비용(추정) |
|---|---|---|
| 지금 방식 (전부 보관) | 약 3TB | 약 $400 |
| **제안 방식** (최근 7일만 원본 + 나머지는 정리본) | **약 220GB** | **약 $30** |

저장 비용만 놓고 보면 **연간 약 500만 원**이 절약됩니다.
여기에 데이터가 적어지면 **조회 속도도 빨라지고, 서버도 덜 필요합니다.**

> 참고: 위 금액은 AWS 공개 단가로 계산한 추정치입니다. 실제 계약 단가에 따라 달라집니다.
> 자세한 계산 근거는 [server-cost-estimate.md](./server-cost-estimate.md)에 있습니다.

## 5. 잃는 것은 없나

**"최근 7일은 원본을 그대로 둔다"**로 하면 실질적인 손실이 없습니다.

- 최근 며칠의 상세한 이동 경로 → 원본이 있으니 그대로 볼 수 있습니다
- 몇 달 전 기록 → "그날 어디 어디에 있었다"는 남습니다. 다만 **1분 단위의 미세한 움직임은 사라집니다**

몇 달 전의 1분 단위 기록이 필요한 경우가 있을지가 판단 기준입니다.
사고나 분쟁이 생겼을 때 근거로 쓰려면 원본이 필요할 수 있는데, 이건 **법무 확인이 필요한 사항**입니다.

## 6. 결정해 주실 것

**① 정리해서 보관하는 방식으로 갈까요?**
→ 가면 서버 비용이 크게 줄고, 조회도 빨라집니다.

**② 원본을 며칠까지 남길까요?**
→ 제안: **7일**. 길게 잡을수록 비용이 늘어납니다 (30일이면 약 4배).

**③ 위치 기록을 법적 근거로 써야 할 일이 있나요?**
→ 있다면 원본 보관 기간을 법무와 상의해서 정해야 합니다. 위치정보법상 보관 의무와도 연결됩니다.

> 이 문서를 검토하다가 **이상징후 알림 규칙에서 구멍을 하나 발견했습니다.**
> 집에만 계신 분은 지금 규칙이면 매일 "위치가 고정됐다"는 알림이 가고, 모니터링 목록에서 빠지지도 않습니다.
> 이 앱의 핵심 사용자에게 기능이 무용지물이 되는 문제라 별도 확인이 필요합니다.
> → [anomaly-alerts.md §6](./anomaly-alerts.md)

## 7. 일정에 미치는 영향

- 앱 수정: 거의 없음
- 서버 작업: **약 1주** (정리 작업을 도는 배치 + 저장 구조)
- **지금 정하는 게 좋습니다.** 나중에 정하면 이미 쌓인 데이터를 다시 정리해야 합니다

## 8. 같이 말씀드릴 사항

방식과 무관하게, **10만 대를 받으려면 서버가 위치를 받는 구조를 한 번 바꿔야 합니다.**

지금은 앱이 보낸 위치를 서버가 곧바로 데이터베이스에 씁니다. 사용자가 많아지면 이 방식으로는 감당이 안 됩니다. 중간에 **대기열**을 두고 모아서 저장하는 구조가 필요합니다. 서버 구성안에도 이미 들어 있는 내용이라 계획을 벗어나지는 않습니다.

이건 서버 담당자와 협의가 필요한 사항입니다.
