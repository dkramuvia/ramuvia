## 1. 서버 구성 (시작)

EC2 1대 (AWS 서울, Amazon Linux) + Docker Compose

```
[인터넷] ── 443 ──> nginx (TLS, WebSocket 중계)
                       │
                       ▼
                    nestjs (API + WebSocket)      worker (위치 일괄 저장, 비상 판정, 파기 배치)
                       │                              │
            ┌──────────┴───────────────┬──────────────┘
            ▼                          ▼
   postgres + PostGIS              redis (현재 위치 캐시, 소켓 서버 간 전달, 인증번호)
   (호스트 포트 노출 안 함, 내부 네트워크만)
```

- DB 포트는 외부에 열지 않는다 (작업지시서 2-1).
- 사진·녹음 파일은 S3 비공개 버킷 + Presigned URL.
- 1대로 시작하므로 SQS 대신 **Redis 큐**로 위치 수신을 버퍼링하고, 코드는 큐 인터페이스 뒤에 두어 나중에 SQS로 교체 가능하게 한다.

## 2. DB 구성: 데이터베이스 2개로 시작

위치만 옮길 수 있게, **처음부터 위치용 데이터베이스를 따로** 만든다. 같은 postgres 서버 안에 있으므로 비용·운영 부담은 같다.

| 데이터베이스 | 스키마 | 담는 것 | 나중에 |
|---|---|---|---|
| `ramupin` (본 DB) | `member` | 회원, 소셜 계정, 약관, 기기(푸시 토큰), 설정, 긴급 연락처 | 이 서버에 유지 |
| | `social` | 친구, 친구 요청, 친구별 공유 설정, 그룹, 그룹 멤버 | 유지 |
| | `chat` | 채팅방, 메시지, 갤러리 게시물·미디어 메타 | 유지 |
| | `geo` | 내가 등록한 장소(안심존·지정 포인트), 회사 지정 구역, 공공데이터 시설 | 유지 |
| | `safety` | SOS 기록, 비상 이벤트, 예약 메시지, 발송 기록 | 유지 |
| | `billing` / `config` | 구독, 영수증, 등급 정책값, 사용자별 정책 덮어쓰기 | 유지 |
| | `admin` | 관리자, 접근 기록, 관공서 조회 계정 | 유지 |
| `ramupin_location` (위치 DB) | `location` | 위치 이력(월 파티션), 체류 장소, 하루 여정 요약, 지오펜스 진입·이탈 기록, 위치정보 이용·제공 사실 확인자료 | **별도 서버로 이전 가능** |

- 스키마를 "데이터베이스 하나 안의 폴더"로만 나누면 JOIN이 가능해서 나중에 떼어내기 어렵다. 위치는 **데이터베이스 자체를 분리**해 두면 처음부터 JOIN이 불가능하므로, 옮길 때 코드가 깨지지 않는다.
- DB 계정: `app_main`(본 DB), `app_location`(위치 DB), `app_migrator`(테이블 변경 전용). 앱 계정에는 DDL 권한을 주지 않는다.
- PostGIS 확장은 두 데이터베이스 모두에 설치한다 (지오펜스 판정, 근처 친구, 경로 거리).

## 3. 코딩 규칙 (위치 DB 분리 대비)

1. **DB 연결 2개**: NestJS 에 `MAIN_DATABASE_URL`, `LOCATION_DATABASE_URL` 두 개를 둔다. 지금은 같은 서버를 가리키고, 이전 시 주소만 바꾼다.
2. **위치 모듈만 위치 DB에 접근**: `location` 모듈 밖에서는 위치 DB 연결을 주입받을 수 없게 한다. 다른 모듈은 `LocationService` 의 함수로만 위치를 조회한다.
3. **DB를 넘나드는 JOIN·외래키 금지**: 위치 테이블의 `user_id` 는 외래키 없이 ID 값만 저장한다. 회원 이름이 필요하면 앱서버에서 두 번 조회해 합친다.
4. **DB를 넘나드는 트랜잭션 금지**: 탈퇴 등 여러 DB를 지워야 하는 작업은 "본 DB 처리 → 위치 DB 삭제 작업을 큐에 등록 → 실패 시 재시도" 순서로 만든다.
5. **마이그레이션 폴더 분리**: `migrations/main`, `migrations/location` 을 따로 관리한다.
6. **위치 쓰기는 큐를 거친다**: API는 받자마자 큐에 넣고 응답, worker 가 모아서 일괄 저장 (GPS 보고서 4장). 현재 위치는 Redis 에 덮어쓰기.
7. **6개월 파기**: 위치 이력은 월 단위 파티션, 오래된 파티션을 통째로 삭제하는 배치를 worker 에 둔다.
8. **ID는 UUID**: 서버가 여러 대·DB가 여러 개가 되어도 충돌하지 않게 한다.

## 4. 이전(분리) 절차 (나중에)

1. 새 DB 서버(RDS 등) 준비, PostGIS 설치
2. `ramupin_location` 데이터베이스를 새 서버로 복제 (덤프 또는 논리 복제)
3. `LOCATION_DATABASE_URL` 을 새 서버로 변경, worker·API 재시작
4. 기존 서버의 `ramupin_location` 삭제

코드 수정 없이 설정 변경만으로 끝나는 것이 목표.

## 5. 외주사·회사에 확인할 것

- 1대 구성에 **Redis 컨테이너**, **postgis 이미지**, **worker 컨테이너** 포함
- 도메인(TLS 인증서, 앱 API 주소), 배포 방법(CI/CD), 1단계 백업(DB 덤프·EBS 스냅샷)
- 서버 1대라도 FCM 푸시·SMS·스토어 영수증 검증 등 외부 호출은 가능해야 함 (Public Subnet EC2 는 가능, 2단계 Private Subnet 전환 시 NAT Gateway 필요)
- 위치 컬럼 암호화 요구 ↔ 공간 쿼리 충돌: 전화번호는 컬럼 암호화, 위치 이력은 암호화, 계산용 좌표는 디스크 암호화로 대응하는 방안 협의
