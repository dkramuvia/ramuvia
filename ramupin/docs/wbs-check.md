## 2. 결정이 필요한 사항 (문서 간 충돌)

개발 전에 확정하지 않으면 다시 작업해야 하는 항목입니다. 각 항목에 **제안**을 함께 적었습니다.

### 2-1. 요금 등급 체계가 문서마다 다름 ★가장 중요

WBS 3.3은 등급 코드를 이렇게 정의합니다: `0 관리자 / 1 일반무료 / 2 일반결제1 / 3 일반결제2 / 4 일반결제3 / 5 노인무료`.
그런데 다른 항목은 `결제1 ~ 결제6`으로 적혀 있고, 피그마에는 플랜이 5개 있습니다.

| 항목 (WBS) | 결제1 | 결제2 | 결제3 | 결제4 | 결제5 | 결제6 |
|---|---|---|---|---|---|---|
| 추정 의미 | 무료 | 유료 1 | 유료 2 | 유료 3 | 노인 무료 | **불명** |
| GPS 전송 주기 (2.4) | 20초 | 20초 | 10초 | 5초 | 5초 | 5초 |

**충돌 내용**
- WBS에는 유료 등급이 3개인데, 피그마에는 일반 유료 플랜이 2개(플래티넘, 트리니티)뿐입니다. 대신 1인 가구 가디언이 추가되어 있어요.
- `결제6`이 무엇인지 WBS에 정의가 없습니다. 관리자인지, 1인 가구인지 확인이 필요해요.
- 숫자가 대부분 서로 다릅니다. 예를 들어 베이직 SOS 인원이 WBS는 2명, 피그마는 1명이고, 무료 사진 용량이 WBS는 불가, 피그마는 300MB입니다.
- 용어도 섞여 있습니다: "장소", "안심 장소", "위치 등록", "지오펜스 알림", "지정 포인트".

**제안**
1. 기획에서 등급 코드와 플랜 이름의 대응표를 한 장으로 확정합니다.
2. 앱에는 숫자를 하나도 넣지 않습니다. 등급별 제한값은 모두 **서버의 플랜 정책 API**로 내려받습니다(WBS 2.1, 11.5, 11.6).
3. 그러면 숫자가 확정되지 않아도 개발을 진행할 수 있습니다. 용어 정리만 먼저 끝내면 돼요.

### 2-2. GPS 전송 방식: 고정 주기 vs 상태 기반

- WBS 2.4는 등급별 **고정 주기**(5초/20초)를 쓰고, 대기 중에는 10~20m 이동 시에만 갱신합니다.
- GPS 보고서는 **상태 기반 적응형**을 제안합니다. 우선순위는 SOS(1~2초) > 지오펜스 근접(3~5초) > 저배터리(3~5분) > 이동 중(15~30초 또는 50~100m) > 정지(1~5분) 순이에요.
- WBS 11.6은 관리자가 사용자별로 전송 주기를 1초~30초 사이에서 바꿀 수 있어야 한다고 합니다.

**제안:** 적응형을 기본 로직으로 삼습니다. 등급별 주기는 "이동 중 최대 주기"로, 관리자 설정은 "사용자별 강제 주기"로 적용해요. 우선순위는 SOS > 관리자 강제 > 적응형 상태 > 등급 기본값입니다. 모든 수치는 서버 정책에서 내려받습니다.

### 2-3. 지도 제스처 충돌 (SOS와 장소 핀)

| 출처 | SOS | 장소 핀 등록 | 핀 삭제 |
|---|---|---|---|
| WBS 7.9 | 화면을 10초간 누름 | - | - |
| WBS 5 | "지도를 누르면 SOS가 실행됨" | 지도를 3번 터치 | 핀을 3초 이상 누름 |
| 피그마 | SOS 버튼 탭 또는 길게 누름, 두 손가락 탭 | 지도를 꾹 누름 | 핀 아이콘을 꾹 누름 |

"지도 누르기"를 SOS, 핀 등록, 채팅의 장소 지정이 함께 쓰고 있어서 **잘못 동작할 위험**이 있습니다.

**제안:**
- SOS는 SOS 버튼(탭 또는 길게 누름)과 두 손가락 탭으로만 실행합니다.
- 지도를 길게 누르면 핀을 등록합니다.
- 핀을 길게 누르면 삭제 확인창이 열립니다.
- 지도를 한 번 누르는 동작에는 기능을 연결하지 않습니다.

### 2-4. 친구 추가 시 기본 위치 공유

- WBS 6.8: 친구가 되어도 내 위치 공유는 **꺼진 상태**(미수락)로 시작합니다.
- 피그마 친구 등록 완료 팝업: "이제 서로의 위치를 알 수 있어요."

**제안:** WBS대로 기본값을 '비공개'로 하고, 팝업 문구를 바꿉니다. 아니면 완료 팝업에서 바로 공유 수준을 고르게 합니다.

### 2-6. 소셜 로그인 종류

**제안:** 11-27 배포 대상에 iOS가 들어가는지 회사에 확인합니다. 들어간다면 Apple 로그인, APNs, 인앱결제 작업을 결제 단계와 함께 진행해야 해요.

## 4. 구현할 때 확인해야 할 기술·정책 제약

| # | 항목 | 내용 | 대응 |
|---|---|---|---|
| T1 | GPS 부가 데이터 | `expo-location`은 위경도, 고도, 정확도, 속도, 방향, 시각만 줍니다. **위치 제공자, 위성 수, 신호 강도, 활동 인식(걷기/차량)은 없어요.** | Expo Modules API로 Android 네이티브 모듈 작성 (FusedLocationProvider, GnssStatus, ActivityRecognition). **2단계에서 가장 먼저 PoC** |
| T2 | 백그라운드 위치 심사 | Play의 "항상 허용" 위치 권한 신고, 포그라운드 서비스(location 유형) 신고, 시연 영상이 필요합니다. 심사가 오래 걸려요. | 2단계 PoC가 끝나면 바로 시연 영상 준비 |
| T3 | 배터리 최적화 예외 | `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`는 Play 정책상 허용 사유가 필요합니다. | 설정 화면으로 안내하는 방식 우선 |
| T4 | 앱에서 직접 문자 발송 | Play 정책상 SMS 권한은 기본 문자 앱이 아니면 거의 승인되지 않습니다. | **긴급 문자와 112/119 발송은 모두 서버에서** (AWS End User Messaging / 국내 문자 업체) |
| T5 | 긴급 전체화면 팝업 | Android 14부터 전체화면 인텐트 권한은 알람·통화 앱 외에는 제한됩니다. | 높은 중요도 알림 + 앱 안 팝업으로 설계. 전체화면 사용 가능 여부는 정책 확인 |
| T6 | 무움직임·GPS 끊김·배터리 방전 감지 | 기기가 꺼지거나 파손되면 앱은 판단할 수 없습니다. | **서버가 "마지막 수신 시각"으로 판정** (§DEVELOPMENT_PLAN 6단계 표) |
| T7 | 카카오·네이버로 나이 확인 | 카카오 출생연도는 비즈 앱 전환과 동의 항목 검수가 필요합니다. 네이버는 동의를 받으면 출생연도를 받을 수 있어요. | 4주 이상 걸릴 수 있으니 바로 신청. 법적 본인확인이 필요하면 PASS 등 본인인증 업체 검토 |
| T8 | 112/119 자동 문자 | 자동 발송이 허위 신고로 처리될 위험이 있고, 기관과 협의가 필요합니다. | WBS 8.4대로 연락처를 비운 채 기능만 준비 |
| T9 | 위치기반서비스 사업 신고 | 위치정보법에 따라 위치기반서비스사업자 신고, 위치기반서비스 약관, 위치정보 관리책임자 지정이 출시 전에 필요합니다. | 회사·법무에 바로 요청 (개발 외 필수 항목) |
| T10 | 광고 정책 | 전체 광고를 "광고 후 메뉴 사용" 방식으로 너무 자주 띄우면 AdMob 정책 위반이 될 수 있습니다. 노인 사용자에게는 광고를 절대 노출하면 안 됩니다. | 노출 빈도를 서버 정책값으로 두고, 광고 SDK는 사용자 등급을 확인한 뒤에만 초기화 |
| T11 | 네이버 지도·Mapbox | 둘 다 네이티브 SDK라 development build가 필요하고, 지도 컴포넌트를 추상화해야 합니다. 네이버 로드뷰는 모바일 SDK 지원 여부를 확인해야 해요. | 1단계에서 `MapView` 추상화, 8단계에서 SDK 추가. **확인 결과(09-16): 네이버 모바일 SDK에는 파노라마가 없어 로드뷰는 지도 JS API 를 WebView 로 띄웁니다** |
| T12 | 채팅 실시간 통신 | 서버 문서에는 SQS와 RDS만 있고, **WebSocket과 Redis가 2차 구성안에 없습니다**(ElastiCache는 확장 시 도입으로 되어 있음). GPS 보고서는 Redis와 WebSocket을 전제로 합니다. | 서버 담당자와 1차 구성에 포함할지 확인 |
