# 위치 수집 서버 비용 추정 (10만 대 기준)

작성: 2026-09-17 · 목적: GPS 전송 방식(적응형 vs 고정 주기) 결정을 위한 근거

> **주의**: 아래 금액은 AWS 서울 리전 공개 단가로 계산한 **추정치**입니다.
> 실제 계약 단가·약정 할인·트래픽 패턴에 따라 달라집니다. 발주 전에는 AWS 요금 계산기로 다시 확인해야 합니다.

## 1. 전제

- 기기 10만 대, 전부 매일 사용
- 하루 중 **이동 2시간 / 정지 22시간** (출퇴근·외출 기준. 실제로는 정지가 더 길 가능성)
- 위치 1건 = DB에서 약 200바이트 (인덱스 포함)
- 위치 보관 6개월 후 파기 (WBS 4.3)

## 3. 월 비용 추정

### 3-1. 저장 비용 (가장 큰 항목)

RDS gp3 스토리지 약 $0.13/GB·월 기준. 6개월치가 다 쌓인 뒤의 정상 상태입니다.

| 방식 | 저장량 | 월 비용 |
|---|---|---|
| **적응형** | 3TB | **약 $400** |
| **09-18 결정** (15초) | 21TB | **약 $2,800** |
| 고정 20초 | 15TB | 약 $1,950 |
| 고정 5초 | 62TB | 약 $8,060 |

백업(스냅샷)을 같은 크기로 잡으면 여기서 더 늘어납니다.

### 3-2. 나머지 항목 (적응형 기준)

| 항목 | 규모 | 월 비용(추정) |
|---|---|---|
| RDS 인스턴스 (db.m6g.xlarge 급, Multi-AZ) | 초당 900건 쓰기를 묶어서 처리 | 약 $500 |
| EC2 API 서버 (t3.large × 3~4대) | 업로드 요청 초당 약 550건 | 약 $350 |
| ALB | - | 약 $30 |
| ElastiCache Redis (현재 위치 캐시) | 10만 명 × 200B ≈ 20MB | 약 $50 |
| SQS | 위치를 100건씩 묶어 보내면 월 2,400만 건 | 약 $10 |
| S3 (사진·녹음) | 사용량에 따라 다름 | 별도 |
| 데이터 전송 | 위치 업로드는 **수신**이라 무료. 조회 트래픽만 과금 | 약 $50 |

**적응형 합계: 월 약 $1,400** (저장 $400 + 나머지 $1,000)

## 4. 지금 구조로는 10만 대를 못 받습니다

방식과 무관하게 아래가 필요합니다.

| 항목 | 현재 | 필요한 것 |
|---|---|---|
| 위치 저장 | ~~API 서버가 DB에 바로 씀~~ → **큐 적용 완료 (09-22)** | 서버를 늘릴 때 Redis Stream → SQS |
| 테이블 | 월 단위 분할, 6개월 후 삭제 | 이미 되어 있음 |
| 앱 전송 | 모아서 한 번에 전송, 실패하면 폰에 보관 | 이미 되어 있음 |
| 친구 위치 조회 | Redis 캐시 | 이미 되어 있음 |

"쌓는 쪽"을 큐로 바꿨습니다 (09-22). **서버 한 대에서도 됩니다** — Redis가 이미 돌고 있고
`appendonly yes` 라 서버가 죽어도 큐 내용이 남습니다.

```
앱 → POST /locations → Redis Stream 에 넣고 바로 응답
                                  ↓
                    워커가 200건씩 모아서 DB 저장
```

**받는 쪽과 저장하는 쪽을 나눈 것**이 핵심이고, 나중에 서버를 늘릴 때는 `XADD` 를 SQS 전송으로
바꾸면 됩니다. 나머지 코드는 그대로입니다.

즉시 처리와 미루는 것을 나눴습니다 (보고서 4-2).

| | 언제 | 왜 |
|---|---|---|
| 현재 위치 (Redis) · 보고 있는 친구에게 전달 | **즉시** | 메모리 작업이라 빠르고, 늦추면 "실시간"이 아님 |
| 이동 경로 저장 (location_points) | 큐 → 워커 | 몇 초 늦어도 아무도 모름 |

**09-22 실제 확인** — DB를 꺼 놓고 위치를 보냈습니다.

| | 결과 |
|---|---|
| 앱 응답 | **201 정상** (DB가 죽은 줄 모름) |
| 큐 | 1건 보관, `저장 실패: ECONNREFUSED` 로그 |
| DB 재시작 후 | 워커가 재시도 → **큐 0건, 전부 저장됨** |

위치가 하나도 사라지지 않았습니다. 큐가 없었다면 앱이 500을 받고 폰 대기열에 남았을 겁니다.

## 5. 비용을 더 줄이는 방법

| 방법 | 효과 | 비고 |
|---|---|---|
| 오래된 위치를 S3로 내리기 | 저장 단가 1/5 ($0.13 → $0.025/GB) | 1개월 지난 데이터는 조회가 드묾 |
| 앱이 더 크게 모아서 보내기 (5~10분) | API 서버 대수 감소 | 실시간성이 조금 떨어짐 |
| 정지 구간을 요약해서 저장 | 저장량 추가 감소 | "언제부터 언제까지 여기 있었다" 1건으로 |
| 보관 기간 단축 | 비례해서 감소 | **위치정보법 확인 필요** (§wbs-check 2-8) |

## 6. 09-18 대표 결정 — 수집 15초 / 전송 60초

대표 지시로 **위치 확인은 15초마다, 서버 전송은 1분마다 모아서** 로 바꿨습니다 (앱 반영 완료).

### 확인과 전송을 나눈 이유

15초마다 서버를 부르면 10만 대 기준 하루 **5억 7,600만 요청**입니다. 확인은 15초로 하되
전송은 60초로 묶으면 요청이 **하루 1억 4,400만 건(1/4)** 으로 줄고, 실시간성은 최대 1분 차이만 생깁니다.
SOS 같은 급한 건은 이 주기와 상관없이 바로 보냅니다.

### 비용 영향

| 항목 | 적응형 | 09-18 결정 |
|---|---|---|
| 하루 저장 건수 (10만 대) | 8,000만 | 5억 7,600만 (7.2배) |
| 6개월 저장량 | 3TB | 21TB |
| 월 비용 | 약 $1,400 | **약 $5,000** |

### 줄이는 방법 — 저장만 요약하면 거의 원래대로 돌아옵니다

비용은 **확인 주기가 아니라 저장 건수**에서 나옵니다. 09-17 실측에서 4시간 270건 중
서로 다른 좌표는 4개뿐이었습니다. 즉 **머문 구간을 "언제부터 언제까지 여기 있었다" 1건으로 합치면**
15초로 확인해도 저장량은 적응형 수준으로 내려갑니다 (월 약 $2,000 예상).

- 확인 15초 — 대표 지시대로 유지 (넘어짐·이탈을 빨리 잡음)
- 전송 60초 — 요청 수 1/4 (적용 완료)
- **저장은 요약** — 서버 작업. `location-storage-proposal.md` 의 제안과 같습니다. **결정 필요**

### 정지 주기는 1분으로 정리했습니다 (09-18)

15초는 **이상징후 판정에 전혀 도움이 되지 않습니다.** 이 문서의 판정 기준이 전부 시간 단위이기 때문입니다.

| 판정 기준 | 시나리오 |
|---|---|
| 30분~1시간 | 28, 33 (신호 두절 1단계) — **문서에서 가장 짧은 기준** |
| 3시간 | 3, 29, 34 |
| 12 / 24 / 48시간 | 나머지 전부 |

"GPS 12시간 고정"을 판정하려면 12시간 동안 50m 안에 있었는지만 알면 됩니다.
3분 간격이면 240건, 15초 간격이면 2,880건 — **판정 결과는 똑같습니다.**
하루 22시간이 머무는 구간이라, **돈이 가장 많이 나가는 구간이 정확히 아무 값어치가 없는 구간**이었습니다.

15초가 실제로 필요한 것은 **보호자 실시간 추적·과속 경고·지오펜스**이고, 전부 이동 중입니다.

| 구간 | 주기 | 근거 |
|---|---|---|
| 이동 중 | **15초** (유료 10초) | 보호자 추적, 과속 경고 |
| 머무는 중 | **60초** | 이상징후 최단 기준 30분의 1/30 |
| 서버 전송 | **60초** | 요청 수 절감 |
| SOS | 2초 + 즉시 전송 | 이 주기와 무관 |

| | 하루 1대 | 10만대 6개월 | 월 비용 |
|---|---|---|---|
| 정지 15초 | 5,760건 | 21TB | $5,000 |
| **정지 60초 (확정)** | **1,800건** | **6.5TB** | **약 $2,300** |

### "집안에서 걸어다니면?" — 같이 막았습니다

활동 인식은 집안에서 화장실·부엌 오가는 것도 `걷기`로 잡습니다.
그것까지 이동으로 치면 집에 계신 분이 하루 종일 15초로 찍혀 절감이 사라집니다.
그래서 **자리를 실제로 벗어났는지(50m)** 를 같이 봅니다.

| 활동 | 판정 | 왜 |
|---|---|---|
| 차량 · 자전거 · 뛰기 | 이동 | 집안에서 나올 수 없는 활동 |
| 걷기 + 50m 넘게 벗어남 | 이동 | 집을 나섬 |
| 걷기 + 제자리 | **머무름** | 집안 이동 |
| 정지 | 머무름 | (50m 밖이면 새 장소에 도착한 것으로 보고 기준점을 옮김) |

기준점은 기기에 저장합니다. 안드로이드가 앱을 죽였다 살려도 남아야, 집을 나선 것을 놓치지 않습니다.

### 주기는 나중에 바꿀 수 있습니다

세 값 모두 앱에 숫자로 박지 않고 서버 `config.plan_policies` 에 들어 있습니다
(`gpsIntervalMovingSec` / `gpsIntervalStillSec` / `uploadIntervalSec`).
**관리자 페이지를 만들었습니다** (`/admin`). 앱 업데이트 없이 등급별·사용자별로 바꿀 수 있고,
누가 언제 무엇을 바꿨는지 이력이 남습니다. 자세한 내용은 [admin-web.md](./admin-web.md).

### 15초를 받으려면 "높은 정확도"로 요청해야 합니다 (09-18 실측)

같은 자리에서 요청 우선순위만 바꿔 비교했습니다.

| 요청 우선순위 | 실제 수집 간격 | 오차 | 측위에 쓴 위성 |
|---|---|---|---|
| 저전력 (Balanced) | 15초를 요청해도 **3~6분에 한 번** | 100m | 0개 |
| **높은 정확도 (High)** | **17초** (23건 연속) | 평균 8m | **0개** |

안드로이드는 폰이 안 움직이면 **저전력으로 요청한 위치를 무시합니다.** 높은 정확도로 요청해야 이 제한이 풀립니다.

**여기서 중요한 점:** 실내에서는 높은 정확도로 요청해도 **위성은 0개**였습니다.
즉 위치를 잡아 준 건 GPS가 아니라 Wi-Fi 이고, "높은 정확도"는 **측위 방식이 아니라 요청의 급(級)** 입니다.
실내에 계시는 동안에는 GPS 칩이 도는 게 아닙니다. 밖으로 나가 위성이 잡히면 그때 GPS가 동원됩니다.

### 배터리 — 중간 측정값이 있습니다

폰 배터리 통계(`dumpsys batterystats`)에서 라무핀 앱 몫입니다.

| 항목 | 값 |
|---|---|
| 측정 구간 | 15시간 39분 (배터리 4,300mAh) |
| 앱이 쓴 전력 | **97 mAh = 배터리의 2.3%** (하루 환산 약 3.5%) |
| **GPS 전력** | **계상 없음** (항목 자체가 안 잡힘) |
| 내역 | 웨이크락 41% · Wi-Fi 36% · CPU 21% · 센서 1% |

**전기를 먹는 건 GPS가 아니라 "앱을 깨우는 것"과 Wi-Fi 스캔입니다.**

> 단, 이 구간은 대부분 **옛 설정(3분 주기)** 으로 돈 값이라 **하한선**입니다.
> 15초로 하루 돌려 본 값이 따로 필요합니다. 일정에 하루 필요합니다.

## 7. 결론

1. **적응형이 저장·서버 비용을 2.5~8배 줄입니다.** 정보 손실은 거의 없습니다 — 가만히 있을 때 같은 좌표를 반복 저장하지 않는 것뿐입니다 (09-17 실측: 4시간 270건 중 서로 다른 좌표는 4개)
2. **어느 방식이든 큐 구조가 필요합니다.** 서버 담당자와 협의 필요
3. 주기 값은 모두 서버 설정이라, 운영하면서 앱 수정 없이 조정할 수 있습니다
4. **09-18 결정(15초)대로 가면 월 $5,000 입니다.** 저장을 요약하면 $2,000 선으로 내려갑니다 (§6)
